# P14 production deployment reference

This is a gated deployment reference for REQ-025, REQ-026, REQ-027, REQ-028, REQ-030 and REQ-031. It records deployable artifacts without asserting that accounts, domains, provider permissions, legal approvals, release evidence, or production credentials exist. Do not synchronize the Render Blueprint, create paid resources, or deploy until the operator inputs and release gates below are complete.

## Artifacts and pinned runtime

- `infra/production/api.Dockerfile` builds with the repository-pinned Node `24.22.0` image digest and pnpm `12.14.0`, runs frozen workspace install, Prisma client generation and API/shared package builds, then creates a production-only workspace deployment. The final image runs as the built-in `node` user.
- `infra/production/worker.Dockerfile` uses the existing Playwright `1.64.0` Noble image digest with the pinned Node `24.22.0` runtime copied in, pnpm `12.14.0`, frozen workspace install and production-only workspace deployment. Chromium and its matching system libraries stay in the runtime; the process runs as `pwuser`.
- Both build contexts use the repository `.dockerignore`, which excludes local `.env` files and host dependency/build directories. Runtime images copy only the production deployment output; credentials are runtime environment inputs, never Docker build arguments or image layers.
- `infra/production/render.yaml` is a reference Blueprint outside the Render default repository-root filename. Select that exact file when registering the Blueprint. It describes API, worker and Keycloak services plus separate paid PostgreSQL 18 app and identity databases. All database addresses and secret values remain operator inputs. Automatic deploys are off; no migration command is attached to service startup.
- `infra/production/identity.Dockerfile` is the production-only Keycloak image. It compiles the credential-revocation provider against the same pinned Keycloak 26.8.1 libraries and builds an optimized image with PostgreSQL, health and metrics options enabled. The local `infra/keycloak/Dockerfile` stays intact for local compose use.
- `apps/web/vercel.json` pins the frozen install and builds shared packages before the Next.js app. In Vercel project settings choose Root Directory `apps/web` and enable “Include source files outside of the Root Directory in the Build Step”; those monorepo settings are dashboard settings, not fields supported by `vercel.json`. Set the Node.js runtime to `24.x` in the Vercel project and verify the build image uses the root `packageManager` pin `pnpm@12.14.0`.

The pinned runtime inventory currently records Node `24.22.0`, pnpm `12.14.0`, Playwright `1.64.0`, Next.js `16.4.2`, NestJS `12.2.0`, pg-boss `12.38.0`, PostgreSQL `18.6` locally, and Keycloak `26.8.1`. Production database services request PostgreSQL major `18`; the provider's exact patch level is operator/platform state. Production Keycloak uses the exact pinned Keycloak and JDK image digests in `infra/production/identity.Dockerfile`.

## Database roles and release sequencing

The app and identity data stores are separate managed PostgreSQL instances, both private-network only (`ipAllowList: []`) and on paid plans. The `0.5c-1g` initial plan is a conservative reference floor, not a measured production capacity recommendation. Confirm connection limits and load before public release.

Provision DB logins using the secure database-owner session and the hidden prompts in `infra/production/bootstrap-app-roles.sql` and `infra/production/bootstrap-identity-role.sql`. The app database separates `trading_migrator`, `trading_api`, and `trading_worker`: migrations create/own application objects; API and worker receive DML plus sequence use; the worker owns only pg-boss's default `pgboss` schema. The one-time app bootstrap briefly grants its named Render bootstrap user membership in `trading_migrator` to install that role's default table/sequence grants, then revokes the membership. The identity DB uses `keycloak_app` on its own database and schema. Do not reuse database owner/bootstrap credentials as runtime `DATABASE_URL` values. Bootstrap scripts are one-time; role rotation is an operator-controlled `ALTER ROLE` procedure through the secure session.

Use separate server-side connection strings: `DATABASE_URL` as `trading_api` for the API, the same key as `trading_worker` for the worker, and Keycloak's `KC_DB_URL`, `KC_DB_USERNAME=keycloak_app`, and `KC_DB_PASSWORD`. Require TLS (`sslmode=verify-full` for PostgreSQL URLs) and private service networking. Never put database URLs in `NEXT_PUBLIC_*`, build args, source files, or Vercel browser bundles.

Release order:

1. Confirm legal/supplier/provider gates, domains, private network, R2 bucket, database credentials, secret values, monitoring, and restore ownership. Set external credentials as runtime secret inputs only.
2. Apply the app role bootstrap, then run the committed Prisma migrations from a controlled release runner with the dedicated `trading_migrator` URL: `pnpm db:migrate`. Do not run migrations as part of the API or worker image command, as a Render pre-deploy hook, or with either runtime role.
3. Deploy the already-built API and worker images manually after migrations are compatible. API readiness is `/api/v1/health/ready`; it intentionally returns not-ready before the expected schema exists. Worker shutdown is bounded by the configured 120-second Render grace period.
4. Provision Keycloak with TLS DB access and a verified fixed `KC_HOSTNAME`; complete realm/client/provider listener configuration and credential-revocation drills before pointing API `OIDC_ISSUER`, `OIDC_REDIRECT_URI`, and `OIDC_ACCOUNT_URL` at it. The repo does not contain a production realm export or operator domain.
5. Configure Vercel with the actual approved application domain and server-only `API_INTERNAL_URL`, `APP_ORIGIN`, `PUBLIC_SITE_URL`, `TRUSTED_INGRESS_SECRET`, and `PUBLICATION_RENDER_HMAC_SECRET`. The latter two values must match the API/worker values for their signed service calls. `API_INTERNAL_URL` must be the actual API HTTPS origin; there is no URL placeholder in this repository.
6. Keep `BILLING_LIVE_APPROVED=false` until live Stripe setup, prices, tax and portal settings, payment approval, and the release review are evidenced. Keep production disabled if any startup guard rejects a missing gate.

The Blueprint sets `autoDeployTrigger: off`. Blueprint synchronization itself can change paid infrastructure, so only an operator with the approved Render account and region should sync it after review. Render auto-creates a service hostname, but the public API and identity URLs and Vercel domain are intentionally absent here. The identity service's `KC_HOSTNAME` must be the real HTTPS host that operators verify and configure. Keep the generated Render identity subdomain disabled after attaching the verified custom domain if both are not intended entry points.

## Operator environment inputs

The Blueprint's `sync: false` values are prompts for the operator's secret manager; they are not examples or committed secrets. Use distinct API and worker DB login URLs and share only explicitly required purpose-bound secrets:

- API: app `DATABASE_URL`; `APP_ORIGIN`, `WEB_ORIGIN`; OIDC issuer/client/redirect/account values; `SESSION_SECRET`, `DATA_ENCRYPTION_KEY`, `PRIVACY_SUPPRESSION_KEY`, `TRUSTED_INGRESS_SECRET`; non-draft approved `TERMS_VERSION`; monitored `SUPPORT_CONTACT_EMAIL` and its monitored flag; `RESEND_WEBHOOK_SECRET` for signed sender webhooks; and Resend SMTP credentials plus the operator's verified sender address. The Blueprint fixes the documented SMTP host, TLS mode, port and username while keeping the password and sender verification as explicit inputs.
- Licensed data: `DATABENTO_API_KEY`, all stock/option/futures datasets, schema mapping, approved capabilities, delay and calendar config. Production startup must reject incomplete or fixture configuration.
- Private objects: `STORAGE_DRIVER=r2`, `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`; use a least-privilege S3 token scoped to this private bucket. Never provide public bucket URLs.
- API billing: Stripe live secret/webhook, account scope, monthly/yearly price IDs, portal configuration and tax state. The live approval boolean stays false until approval evidence is recorded.
- Worker: worker-role `DATABASE_URL`; `DATA_ENCRYPTION_KEY`; matching session, suppression, trusted-ingress and publication-render HMAC secrets; `MARKET_DATA_PROVIDER=databento`, `BILLING_PROVIDER=stripe`, `BILLING_MODE=live`, and the correct Stripe account scope; operator-configured internal `PUBLICATION_API_BASE_URL`, actual `PUBLICATION_RENDER_BASE_URL`; verified sender and authenticated TLS SMTP password.
- Both API and worker require `BACKUP_POLICY_REVIEWED=true` only after an operator reviews the backup policy, and a real `DEPLOYMENT_REVISION` matching the deployed immutable source revision. Keep these as operator inputs; do not use fabricated values to pass startup checks.
- Keycloak: operator-controlled TLS `KC_DB_URL`, `KC_DB_PASSWORD`, fixed `KC_HOSTNAME`, one-time bootstrap administrator username/password. Remove or rotate bootstrap credentials after the first administrator is provisioned; do not place a realm import secret in the image. In the production realm, enable the `trading-community-credential-revocation` event listener and configure the application OIDC client with `trading-community.credential-revocation=true`, backchannel logout enabled, and backchannel URL set to the actual API origin plus `/api/v1/webhooks/oidc/logout`; set `backchannel.logout.session.required=false`. Keep public subject mapping. The endpoint and listener must be tested with the P04 credential-revocation drills before the realm is used for production logins.
- Vercel server runtime: actual `API_INTERNAL_URL`, `APP_ORIGIN`, `PUBLIC_SITE_URL`, `RELEASE_MODE=production`, `WEB_INGRESS_MODE`, `TRUSTED_INGRESS_SECRET`, and `PUBLICATION_RENDER_HMAC_SECRET`. Enable `HSTS_ENABLED` only after all production domains and TLS redirects are verified. Do not expose server credentials as `NEXT_PUBLIC_*` values.

Render's manifest explicitly keeps live billing approval false and requests operator-supplied secrets. It is intentionally incomplete until these values, provider contracts and accepted policy copy exist. No synthetic account, supplier approval, prices, hostname, or service URL is invented by the artifact.

## TLS, object recovery and account erasure

Use HTTPS for Vercel, public API, Keycloak and provider callback URLs; configure the API's trusted ingress rules for the actual Vercel ingress chain, and do not trust arbitrary forwarded client IP headers. Keycloak is started in optimized production mode with strict hostname and `xforwarded` proxy header handling; the edge must overwrite the trusted forwarding headers. Render's Postgres service URLs must use TLS and remain private-network connections.

Create the Cloudflare R2 bucket separately, with public `r2.dev` access disabled, no public custom domain, no bucket listing, and separate least-privilege API credentials. R2 public access is opt-in; keep it disabled for media and exports. Set the product's short retention/lifecycle behavior only after confirming it does not conflict with deletion duties. The adapter creates no direct or presigned public object URLs.

The R2 bucket is not a backup. Establish a separately administered encrypted object-copy policy and test restore of media/export objects before release. Back up the privacy suppression ledger using a separate key/account/location from both the database and object store; verify that it can be recovered before any database restore. Never restore user rows and resume ingress before applying the suppression ledger and completing queued erasures. Keep the suppression HMAC key stable and separately backed up; losing it makes restored-account suppression unverifiable.

Render paid Postgres supports PITR, but the recovery window depends on the workspace plan: Hobby is three days and Pro or higher is seven days. The requested seven-day target therefore requires the Render Pro-or-higher workspace tier; the Blueprint's paid database plan alone does not prove this retention. Confirm the dashboard window for each database. Render PITR creates a separate recovery instance; validate it before switching traffic. Also create independent encrypted logical exports for portability and protect those exports under the approved retention policy. Record measured RPO/RTO only after a full restore rehearsal.

## Rollback and recovery

Migrations are forward-only and must remain additive/backward-compatible across the rollout window. Roll back API/worker image versions only while the current schema remains compatible with that image. For a failed destructive or incompatible change, stop external traffic, recover a separate database instance, apply the separately stored suppression ledger, finish erasure work, validate identity/billing/object references, and then change runtime connection URLs. Do not run an improvised down migration or point production at an unverified PITR recovery.

R2 recovery is a separate restore path from Postgres: restore the needed private object keys and metadata, run orphan/retention reconciliation, then verify owner/purpose authorization through the API. Test deletion of an account before and after object restore so restored private objects cannot reappear through a valid API route. A backup that has not been restored does not establish recovery readiness.
