# P14 local recovery and service-load drills

These harnesses measure the local Docker/PostgreSQL implementation with synthetic data. They do not close G09, establish production backup/object recovery, or claim production RPO/RTO. The recovery script reports its local checkpoint-to-verification elapsed time and estimated checkpoint loss window. The load script reports PostgreSQL-backed API service timings; it does not measure rendered browser LCP.

## Preconditions

Use a healthy local Compose environment initialized from `.env.local`. Complete dependency installation, Prisma generation, current migrations, shared/API/worker builds, and fixture seed before beginning. Keep worker and API images available. Run the scripts serially; they allocate large databases and the recovery drill exercises real worker privacy erasure code. They only create/drop uniquely generated `p14_source_*`, `p14_restore_*`, or `p14_load_*` databases. They do not reset Docker volumes or connect to a production database. If setup fails, inspect that only generated names remain before retrying.

The recovery drill starts from an empty generated source database, deploys current migrations and synthetic seed there, creates two synthetic owners plus frozen publication history, a private journal row, an authenticated application session and a synthetic object, and takes a custom-format `pg_dump` checkpoint plus a separate synthetic object checkpoint. It checks the processed object SHA-256 after restoring that object checkpoint. A synthetic committed watermark before the dump and a second commit after it verify restored checkpoint data and the later marker's absence; their timestamp gap is a local synthetic boundary measurement, not an actual production data-loss window. The drill then runs the existing worker erasure stages on the source and captures the resulting keyed suppression ledger. The database checkpoint is restored to a second generated database; the existing suppression importer queues the restored deletion and the existing worker sweep removes private data and restored object bytes. The final checks call the existing `AuthService.authenticate` with the captured synthetic session token and require rejection, alongside revoked session state, erased private journal/object data, hidden and redacted public derivatives, preserved frozen financial terms, and an intact unrelated owner. This exercises local app-session authentication; it does not run a new OIDC-provider login. The original configured app database is not a fixture target.

Run the local restore rehearsal:

```sh
node scripts/p14-recovery-local.mjs
```

Run the representative service load separately:

```sh
node scripts/p14-load-local.mjs
```

The load fixture has 5,000 explicitly synthetic accounts, 1,000 accounts with a recent valid application session as the MAU proxy, 1,000 session rows, 100 concurrent authenticated API-service requests, 50,000 public trade publications, 50,000 linked pending public positions, 25,000 option position legs, and 250,000 comments. It defaults to the API's configured 8-connection pool; set `P14_LOAD_POOL_MAX=20` for a separate larger-pool comparison. Before seeding the publications it resolves the current synthetic fixture metadata and validates frozen plans with the existing `hydrateTradePlan`. The exact plan mix is 20,000 stocks, 15,000 futures, and 15,000 options. Futures use the four seeded December 2026 ES/MES/NQ/MNQ contracts. Options are balanced at 2,500 each across `long_call`, `long_put`, `bull_call_debit`, `bear_put_debit`, `bull_put_credit`, and `bear_call_credit`, with real seeded November 20, 2026 option contract references. The capability preflight verifies existing public display/chart/snapshot and member publishing fixture rights; it adds no capability rows. Position initial risk is computed with the existing domain `calculatePosition` using each hydrated plan, positions remain `pending`, and the fixture includes no position events or outcome snapshots.

After loading, the harness runs PostgreSQL `ANALYZE`, then uses a 40% public-feed, 20% publication-search, 20% chart-history, 10% private-read and 10% private-write mix. It calls `JournalService`, `PublicationService`, `InstrumentService.bars` and `AuthService.authenticate`, and checks that separate owners cannot read one another's journal entries. The report includes p50/p95 durations by operation and pool checkout wait, write-batch time and total mixed-request elapsed time; it enforces ordinary service p95 below 750 ms and search p95 below 1,000 ms, plus required operation sample counts; a miss exits nonzero after cleanup and includes failed checks in the report. This is an in-process service and database workload, not HTTP/browser or production capacity evidence.

One local pool-8 mixed run measured feed p95 at 427.2 ms, search p95 at 427.4 ms, chart history p95 at 284.1 ms, authenticated private read p95 at 290.7 ms, authenticated private write p95 at 225.9 ms, and session authentication p95 at 18.4 ms. The 100-request mix completed in 444.8 ms; concurrent pool checkout wait p95 was 103.6 ms. These measurements were below the stated local service and search targets for this run. The initial safe output is retained at `/tmp/options-p14-load-mixed.log`; earlier attempts in that same log stopped on a harness query alias issue and cleaned their generated databases before the successful run. A final repeat with enforced exit status passed at feed/search p95 463.6/464.0 ms, chart 298.3 ms, private read/write 302.8/226.2 ms, auth 22.9 ms and pool wait 101.5 ms. The durable [final JSON](../implementation/artifacts/P14/service-load-mixed.json) records all sample/threshold checks. These local synthetic bursts do not establish production performance or capacity.

Both commands remove only their generated databases in `finally` cleanup. Recovery scratch dumps/ledger files use a private temporary directory and the synthetic object tree uses a unique `/tmp/p14-recovery-*` path inside the API container. Never copy a production backup into these drills. If a process is interrupted, identify the exact generated `p14_*` database name from its output/Compose logs and remove only that database after confirming the name; preserve the configured app and identity databases and all volumes.

Record the full command, actual exit status, measured values, Docker/PostgreSQL/app revision, operator and any failed checks in [P14 evidence](../implementation/evidence/P14.md). A successful local result is local synthetic evidence only. Production still requires a separately held current suppression ledger and key, real processed-object restoration, provider billing reconciliation without duplicate side effects, measured managed-service RPO/RTO, trusted ingress and the remaining external release approvals.
