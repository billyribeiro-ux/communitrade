# ADR 0022: Notifications, SMTP delivery uncertainty and consented measurement

Date: October 20, 2026. Status: engineering implementation; actual local checks are recorded in [P11 evidence](../implementation/evidence/P11.md).

## Decision

Business transactions append notification outbox events without contacting SMTP. pg-boss fanout locks an outbox row and commits recipient aggregation/read state with delivery acknowledgment atomically. The event UUID and persisted attempt determine a stable queue identity, so enqueue-before-ack replay cannot create another business event. Reply/mention aggregation uses source, actor and UTC day; distinct transactional events keep distinct identities. Current source visibility and the exact publication data-rights boundary are rechecked before presenting a public link. Generic activity notices carry no comment body or private journal content.

Email has a separate SideEffectDelivery ledger, bounded to five attempts within 24 hours of its first attempt. Stable business keys and Message-ID values suppress routine duplicates; they do not provide SMTP exactly-once delivery. Accepted SMTP followed by lost database acknowledgment, stale processing claims, and uncertain DATA acknowledgments become `uncertain`. Automatic and staff retry cannot resend an uncertain message. Operators reconcile transport evidence before any future recovery workflow. Deterministic queue UUIDs are derived from delivery and attempt; database enqueue-ack failures retain that UUID.

Daily digest is optional, default off, fixed at 08:00 in the current IANA timezone, delayed by quiet hours (default 22:00–08:00). There is one durable key per owner/local date, including DST and timezone changes. Current opt-in, suppression, owner status, public-source rights, mutes, entitlement and quiet hours are checked again before sending. Free gets followed-author activity; Pro adds up to five private saved public searches. A signed expiring digest-unsubscribe token requires an explicit POST confirmation; loading the link makes no change. The confirmation route is no-store, no-referrer and noindex, including in production. Security/account/billing notices remain mandatory, while recipient bounce suppression protects all email. Production SMTP requires verified sender configuration and authenticated TLS. Local SMTP only uses Mailpit and synthetic `.invalid` recipients.

First-party ProductEvent names are activation, return, publication, review, report, conversion and churn. Collection requires current versioned opt-in; withdrawal serializes against event insertion and deletes retained owner events. Only bounded asset/strategy/plan/surface enums are allowed. Business source keys are hashed and deduplicated per owner/event; private thesis, notes, titles, URLs, handles and credentials are rejected. Events expire after 90 days. Activation follows the MVP definition: at least three followed authors/instruments, then a trusted publication/comment/journal creation within seven days of joining. Onboarding asset interests alone do not count as follows. Repeated contributions share one activation identity. Browser input can only report return; other events require trusted domain transactions. Conversion/churn integration belongs to the P12 billing lifecycle.

Admin job views expose safe status, attempts, codes and aggregate backlog counts, never recipient addresses or job payloads. Recent MFA, current admin role, CSRF, idempotency, bounded original retry budgets and immutable reasoned audit records protect retries. Publication/media evidence uses its existing member recovery workflow instead of resetting frozen evidence through a generic staff action.

The trusted renderer pairs its readiness marker and capture callback under one lifecycle owner. Setup/cleanup removes stale markers, readiness publishes the callback only after initialization/paint, and stale cleanup cannot remove a newer instance. The worker checks readiness and invokes capture atomically in one browser call, with a bounded five-second retry for transient readiness loss. This fixes the observed development remount races without weakening single-use signed render claims. Structured browser capture results preserve safe error codes across the SDK boundary; server claim/candidate failures expose bounded diagnostics without signed URLs. Read-all keeps its cutoff entirely in PostgreSQL to preserve microsecond precision.

## Consequences

No Redis or new service is required. Nodemailer is an exact-pinned replaceable SMTP adapter. Delivery workers and notification sources depend on the API's authenticated internal source-authorization endpoint; failure is closed and retried within budget. Real sender verification, provider bounce/complaint webhook integration and deliverability acceptance remain release gates. No Phase 2 streaming, scanners, push/SMS, broker integration or payout behavior is added.
