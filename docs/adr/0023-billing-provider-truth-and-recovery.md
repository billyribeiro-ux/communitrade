# ADR 0023: Provider-scoped billing truth, bounded access and uncertain operations

Date: October 20, 2026. Status: engineering implementation; actual acceptance is tracked in [P12 evidence](../implementation/evidence/P12.md). Supplements [ADR 0006](0006-billing-entitlements.md).

## Decision

The API owns monthly/annual price selection, verified identity, current terms acceptance and subscription ownership. Checkout/portal return URLs come from the configured application origin. Loading a return page never grants access. The provider adapter supplies current subscription, invoice, refund and dispute truth; signed events trigger reconciliation rather than applying their potentially old status directly. Event identities are unique within the configured provider account and test/live mode. Raw request bytes are preserved before JSON parsing for signature verification.

Billing operations are durable before contacting a provider and retain stable idempotency keys across uncertain responses. A new request must not create another checkout while an earlier session is open or its outcome is uncertain. Unknown mutation results are reconciled; an expired provider idempotency window is not permission to repeat a refund or purchase. Staff cannot edit local Pro flags. Refund and cancellation are separate explicit actions, authorized by current administrator role, recent MFA, CSRF, an immutable support reason and command idempotency. Payment ownership includes subscription, customer, provider account and mode.

Active/trialing access is bounded by its processor period. No trial is offered by default. Paid-through cancellation uses actual paid access, not the next unpaid billed period. Failed renewals preserve existing paid access for a fixed 72-hour first-failure window; duplicate or delayed messages cannot extend it. Unpaid/incomplete-expired access becomes Free. Every API and worker entitlement read applies the same configured account/mode and validity boundary, so access expires even if a scheduled sweep is unavailable. Historical deterministic personas remain usable only in the original local synthetic scope; public/production mode excludes them. Downgrade preserves saved records, owner edits and raw personal export while restricting new additions and Pro analytical features.

A bounded worker-authenticated API sweep reconciles failed events, uncertain operations and current customers. The worker sends no user-selected entitlement state. Billing changes produce deduplicated mandatory account notices and consented conversion/churn events through P11's existing boundaries. Staff billing data excludes private journal content and payment credentials.

The local fake adapter persists separate synthetic provider state in PostgreSQL. Its checkout and portal require explicit owner-authenticated, CSRF-protected confirmation. It uses signed synthetic events through the same reconciliation path; no redirect, fixture array or browser state can activate Pro. Fake billing is prohibited in public/production mode. Stripe uses a pinned documented API version and native server fetch/crypto, without adding a client payment SDK or collecting card data.

## Consequences

Local test-mode lifecycle acceptance can finish without a real purchase or processor credentials. This does not establish processor underwriting, production price/tax/portal configuration, legal copy approval or real deliverability. Those remain named release gates. Provider-specific fields stay behind BillingPort; migration history, original publications and private records are preserved. No marketplace, creator payouts, broker integration or Phase 2 feature is included.

## Regression hardening during P12

P11's connected regression exposed development refreshes re-rendering an already-claimed, one-use snapshot page. Next 16.4.2 transports its React Flight debug stream over the HMR WebSocket. Blocking the entire stream left hydration waiting; disabling the debug channel instead inlined development debug data, which the session-secrecy SSR check rejected. That configuration experiment was reverted. The worker now connects only to the configured renderer origin's exact `/_next/hmr` WebSocket and relays only the pinned binary `REACT_DEBUG_CHUNK` frame type (0 with a valid request-ID envelope). It discards every textual hot-update/reload message, other binary frame types and all browser-to-server messages. Other WebSockets remain inert with no upstream connection. Server close events do not trigger the client's reconnect/reload loop. HTTP remains restricted to same-origin GET/HEAD resources. Production Next does not use this development channel. This is an explicitly version-bound compatibility boundary: a Next upgrade must repeat the trusted-capture and session-secrecy regressions. Normal application development still supports HMR; only frozen worker capture filters it. Signed render claims remain single-use; no permission or claim check is weakened. This is product capture behavior, not a replacement for blocked manual browser acceptance.

The synthetic processor serializes refunds by locking the scoped invoice row in the same PostgreSQL transaction before reading prior refunds. Different command keys cannot overrun the remaining refundable amount. Stripe and fake refund evidence include the durable operation ID, enabling recovery to prove a prior mutation before retrying it. Migration 020 is additive; migration 019 remains immutable.
