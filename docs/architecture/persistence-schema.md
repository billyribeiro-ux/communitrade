# Persistence schema implementation notes

This document describes the Prisma model and the PostgreSQL rules that complete it. The authoritative business semantics remain in the [data model](data-model.md), [API contract](api-contract.md), and [security/privacy contract](../quality/security-and-privacy.md). The schema is additive after the P01 `foundation_probe` migration. Product tables use UUID identifiers, UTC `timestamptz(6)` timestamps, optimistic integer revisions, and `numeric(28,10)` for financial values. Client JSON boundaries represent decimals as strings.

Prisma model names are the application delegates; the mapped table names are the database names. `user_account` keeps OIDC identity and private email state. `profile` contains public-facing profile fields. `synthetic` marks deterministic local seed accounts, whose issuer is also a reserved synthetic issuer. Synthetic data is not valid production evidence.

## SQL rules not expressible in the Prisma model

The migrations contain reviewed SQL for these constraints and triggers. Prisma schema validation checks the model shape; it does not encode every PostgreSQL invariant below. Keep these additions when preparing any later migration and compare the generated migration against the full history before applying it.

- `user_account.status`, instrument asset, position state, publication kind/visibility, event type, and outbox status values are checked. Quota/rate-limit counts and quantities are bounded and nonnegative; supplied prices and costs cannot be negative; null cost remains null.
- Quota uniqueness is `(user_id, metric, month_start)`; the month key is a UTC `timestamptz`. Idempotency uniqueness is `(actor_key, route, key)`. Outbox delivery intent is unique by event, aggregate, and revision; side-effect delivery is unique by channel/business key. Conditional quota upserts and row locks are performed by transaction code.
- Private aggregate owner IDs have explicit user foreign keys. The SQL supplement adds foreign keys for scalar references Prisma does not model as relations, including instrument, publication, position, journal, event, media, support, moderation, and entitlement relationships. Missing or cross-owner private access must still be rejected by server services.
- A position names exactly one public publication or private journal source. The owner must match that publication's author or the journal owner. Its metadata version and instrument must match; each leg's metadata version must belong to that leg's instrument. Initial risk is positive when present, required for entered/closed/unresolved states, and cannot change once established, including after a state change.
- Comment edits increment a positive revision for If-Match checks. Positions expose both optimistic revision and an update timestamp. Published chart states cannot change. Publication versions, position events, audit events, and instrument metadata versions are append-only; corrections create a new visible version. Version pointers and previous-version references are constrained to the same publication. Event supersession remains within one position. Comment reply/root references remain within one publication.
- Follow rows have exactly one target; self-follow, self-mute, and self-repost are rejected. Reposts have one active row per actor/source. Ready media requires a processed object key.
- Timestamps for expiry, grace, publication, session, event, and delivery use UTC `timestamptz(6)`. The public publication-version text index contains frozen publication text only; all query results still join through current publication visibility and data-capability checks. The partial outbox index excludes delivered events.

## Migration sequence and seed boundaries

`202610190001_foundation` creates only the original operational probe. `202610190002_domain` creates the product aggregates and adds ownership, history, uniqueness, and business constraints. `202610190003_catalog_history` adds the fixture marker, complete option/futures metadata, UTC expiry, catalog checks, and stronger immutability. `202610190004_utc_and_indexes` normalizes the last naive timestamps and adds public-text/outbox indexes. `202610190005_revision_clocks` adds comment edit revisions and a position update clock. `202610190006_risk_freeze` prevents state changes unlocking an established denominator. `pg-boss` tables and migrations remain owned by pg-boss; Keycloak uses its separate identity database.

The API seed preserves the P01 probe and creates fixed synthetic personas, Free/Pro entitlement examples, role examples, a stock, four supported futures roots, and standard call/put contracts at two strikes. It refuses to run when `NODE_ENV=production` or `RELEASE_MODE=production`. The shared calculation source is [`contracts/fixtures/domain-calculations.json`](../../contracts/fixtures/domain-calculations.json); the API fixture test checks its cases for exact equality with the API persona fixture, avoiding two drifting sets of financial expectations. No seed row represents a real user, supplier quote, broker execution, or verified performance.

## P03 additive contact intake

Migration `202610190007_contact_receipts` adds private requester email, subject, consent version and timestamp to SupportTicket, with bounded lengths and paired consent fields. Public contact returns only its submission receipt, not an authorization token. Existing IdempotencyRecord and RateLimitBucket tables provide durable retry/rate enforcement. [ADR 0014](../adr/0014-preview-shell-contact-intent.md) explains the boundary and P13 retention/owner/staff integration. No existing migration was edited.

## P04 identity and media lifecycle

Migration `202610200008_identity_media` adds `OidcLogoutReplay` and `PolicyAcceptance` (51 Prisma models total), provider-session lookup, media declared MIME/byte bounds, expiry, failure and update metadata/indexes. The replay ledger prevents reuse of accepted signed provider logout events; versioned policy acceptance is private owner evidence. Migration `202610200009_privilege_revocation` adds triggers that revoke affected opaque sessions on role changes, account status/email changes and removal of email verification. Earlier migrations remain immutable. [ADR 0015](../adr/0015-identity-profile-media.md) records the implementation.

## P05 explicit supplier identity

Migration `202610200010_provider_instrument_mapping` adds `ProviderInstrumentMapping` (52 models total). A mapping ties an internal instrument UUID and exact immutable metadata version to supplier, dataset and raw symbol, with effective/revocation times. A composite foreign key prevents cross-instrument metadata references. Identity/mapping fields are immutable, deletion is denied and a mapping can be revoked once; corrections append a new mapping. Active mapping lookup does not infer symbols from tickers or UUID prefixes.

The expanded synthetic seed preserves the original nine instrument identities and all v1 snapshots. It adds four March-2027 futures and eight option contracts, giving one underlying, twelve options across two expirations and eight dated futures. December-2026 quarterly futures retain v1 and gain v2 with the corrected 09:30 New York last-trade boundary. Independent synthetic agreement rows cover public/member and each use purpose, plus calendar display; they are not valid production licenses. Public release mode now rejects synthetic seeding/records as well as production mode. See [P05](../implementation/evidence/P05.md).

## P08 publication and reporting

Additive migrations `202610200011_p08_publication_jobs`, `202610200012_p08_correction_publication_job`, and `202610200013_p08_position_provenance` bring the inventory to 53 Prisma models and thirteen migrations. `PublicationJob` freezes a private immutable candidate, owner/draft/version references, nonce/claim, attempts/failure and trusted artifact binding. Draft attachment IDs are checked against owned ready processed draft media; media resource_type distinguishes the attachment lifecycle. PositionEvent.details holds explicitly reported resolution/borrow-cost context. Correction requests retain reviewer reason and publication job reference. Position.risk_source_version_id and OutcomeSnapshot.publication_version_id retain separate frozen-risk and calculation provenance. Candidate/image immutability and attachment ownership guards supplement server authorization. Earlier applied migrations remain unchanged.

## P09 community and discovery

Migration `202610200014_p09_community` adds CommentMention and CommentEditHistory (55 models/fourteen migrations), report detail, partial author/instrument follow uniqueness and matching immutable-expression GIN indexes for current-public title/thesis and public author search. Existing comment revision/root/target/tombstone, reaction/bookmark/mute uniqueness and one-active-repost constraints are reused. Shared rate-limit buckets enforce comment/report caps transactionally. No position/outcome/publication clone is created by a repost. Source authorization remains live, with no persistent search/share/discovery content cache. See [ADR 0020](../adr/0020-community-distribution-and-source-visibility.md).

## P10 journal and export execution

Additive migrations `202610200015_p10_workspace`, `202610200016_p10_exports` and `202610200017_p10_export_fencing` retain 55 Prisma models and bring the ordered migration inventory to seventeen. They add journal private title/thesis/deletion, active owner/source uniqueness and field bounds, watchlist/layout update timestamps and positive revision checks, and durable export timestamps/claim metadata/status/kind/expiry/size/key constraints. Migration 017 permits immutable per-attempt export objects without changing applied migration 016. No previously applied migration is edited. Exact six-digit timestamp cursors preserve PostgreSQL precision. Seed reruns add dedicated synthetic quota-exhausted and downgraded collection owners without replacing their edited records. [P10 evidence](../implementation/evidence/P10.md) records actual migration and clean-database verification.


## P11 durable notifications and measurement

Migration `202610200018_p11_notifications` brings the inventory to 59 models/eighteen migrations. Notification gains generic text, source pointer, event count and activity clock; owner/unread indexes support precise cursor pages. SavedSearch has owner/revision, bounded structured public filters and case-insensitive owner/name uniqueness. DigestSuppression and EmailSuppression distinguish optional unsubscribe from transport suppression. SideEffectDelivery gains owner/category, payload, claim/queue IDs, retry clocks/budgets and explicit pending/queued/processing/succeeded/failed/suppressed/uncertain states. ProductEvent has versioned consent, bounded enum properties, hashed source key, per-owner/event dedupe and retention indexes. The outbox constraint adds queued; no applied earlier migration is edited. Daily-digest local-date uniqueness uses the existing channel/business-key ledger rather than another duplicate delivery table. [P11 evidence](../implementation/evidence/P11.md) records executed checks.

## P12 billing persistence

Additive migrations `202610200019_p12_billing` and `202610200020_billing_refund_operation` bring the inventory to **72 models/twenty migrations**. Applied earlier SQL remains immutable. Billing customer/subscription/invoice/refund/dispute/event/operation records are scoped by provider-prefixed account and test/live mode. Operations retain request identity, original resolved refund amount, retry clocks, provider references and outcome evidence before external writes. Event reconciliation uses exact raw-byte signature verification before persisted processing. SubscriptionEntitlement adds the same account/mode scope and bounded Pro validity; legacy deterministic defaults are confined to local fake mode at every API/worker read.

The fake processor stores separate customers, sessions, subscriptions, invoices, refunds, disputes, signed events and idempotent operations. Owner identities are foreign-keyed; synthetic provider records are not treated as production payment evidence. Migration 020 links fake refund operation IDs to durable business operations for lost-ack recovery. Production Stripe uses metadata for that linkage. No real card data or payment secrets are stored in application tables. See [ADR 0023](../adr/0023-billing-provider-truth-and-recovery.md) and [P12 evidence](../implementation/evidence/P12.md).

## P13 staff, support and privacy persistence

Additive migrations 021–024 bring the inventory to **75 models and 24 migrations**. Staff assignment/decision columns and reversible profile/repost markers support scoped queues. `moderation_hidden` distinguishes staff publication hiding from owner hiding and erasure. `SupportAccessGrant` persists the owner request, specific resource/purpose, named staff principal, decision and <=1-hour expiry. Tickets retain explicit staff-message attribution and update/assignment state; contact receipts use a private durable delivery ledger.

Privacy requests persist request/deadline/finite hold, command identity, claim/checkpoint and safe failure state. `PrivacyDeletionObject` retains deletion inventory until storage confirms erasure. `PrivacyDeletionSuppression` stores HMAC subject identity and key version for authentication and restored-backup suppression. JSON archives reuse owner-scoped ExportJob. Normal frozen-record immutability remains; narrow stage/owner/exact-redaction guards permit approved erasure without arbitrary history mutation. Migration 024 replaces nested financial projection with a fixed safe field allowlist. Previously successful migrations were not rewritten. See [ADR 0024](../adr/0024-staff-support-privacy-control.md).

## P14 operational boundaries

Migration 025 adds shared trusted ingress nonces, minimal Resend event replay metadata and keyed address suppression (including anonymous support recipients). **78 models / 25 migrations** are now defined. Nonces expire after two minutes; a bounded worker purge removes expired nonces and 30-day webhook replay records. Suppression retains only a purpose-keyed digest and reason; no raw email/message body is stored. The stable key and suppression state require independent recovery custody. Earlier successful SQL remains immutable.
